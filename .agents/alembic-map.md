# Alembic Navigation Map

Source lives in the active venv's `site-packages/alembic/`. The version actually being investigated is whatever `importlib.metadata.version("alembic")` returns at read time.

## How to use this map

This map targets Alembic 1.x. The high-level layout (`ddl/`, `operations/`, `autogenerate/`, `runtime/`, `script/`, `command.py`, `config.py`, `op.py`) has been stable across recent minor versions, and most entries below should apply across them. The long tail drifts: occasional file splits in `autogenerate/compare/`, new operation classes, renamed private helpers.

Paths are relative to `site-packages/alembic/`. Before relying on a specific file or class pointer, sanity-check that it still exists at the installed version. If a cited path is missing, tell the user the map is out of date for that area and suggest updating the map rather than guessing a replacement.

Cite file paths and class or function names in your answers. Do not cite line numbers, they rot.

## Dialect implementation layer (where third-party dialects plug in)

- **`DefaultImpl` — the contract every dialect impl must satisfy**: `ddl/impl.py`. This is the central extension surface. A ClickHouse impl subclasses `DefaultImpl` and sets `__dialect__ = "clickhouse"`. The `ImplMeta` metaclass registers subclasses by `__dialect__`. Important overridable methods: `add_column`, `drop_column`, `alter_column`, `add_constraint`, `drop_constraint`, `rename_table`, `create_table`, `drop_table`, `create_index`, `drop_index`, `bulk_insert`, `compare_server_default`, `compare_type`, `correct_for_autogen_constraints`, `correct_for_autogen_foreignkeys`, `start_migrations`, `emit_begin`, `emit_commit`, `_exec`, `static_output`.
- **Per-dialect impls (reference implementations)**: `ddl/postgresql.py`, `ddl/mysql.py`, `ddl/sqlite.py`, `ddl/mssql.py`, `ddl/oracle.py`. Read these to see what `DefaultImpl` looks like when fully overridden. PostgreSQL is the closest analogue for non-standard features.
- **Common DDL elements consumed by impls**: `ddl/base.py`. `AlterTable`, `RenameTable`, `AlterColumn`, `ColumnNullable`, `ColumnType`, `ColumnName`, `ColumnDefault`, `AddColumn`, `DropColumn`, `ColumnComment`, plus the `visit_*` functions that compile them. These are SQLAlchemy `DDLElement`s, registered to compile via `@compiles`.

## Operations API (the `op.*` surface used inside migration scripts)

- **Operation classes (data carriers)**: `operations/ops.py`. `MigrateOperation` is the root. Concrete ops: `CreateTableOp`, `DropTableOp`, `RenameTableOp`, `AddColumnOp`, `DropColumnOp`, `AlterColumnOp`, `CreateIndexOp`, `DropIndexOp`, `AddConstraintOp`, `DropConstraintOp`, `CreatePrimaryKeyOp`, `CreateUniqueConstraintOp`, `CreateForeignKeyOp`, `CreateCheckConstraintOp`, `CreateTableCommentOp` / `DropTableCommentOp`, `BulkInsertOp`, `ExecuteSQLOp`. Containers: `OpContainer`, `ModifyTableOps`, `UpgradeOps`, `DowngradeOps`, `MigrationScript`.
- **`Operations` / `AbstractOperations` (the `op` proxy)**: `operations/base.py`. `Operations` exposes the migration-script API (`op.create_table`, `op.add_column`, `op.execute`, etc.). `AbstractOperations.implementation_for(op_class)` is the decorator that wires an op class to its execution function. `BatchOperations` is the batch-mode (alter-via-copy) variant for backends that can't do many ALTERs.
- **Operation → impl dispatch**: `operations/toimpl.py`. Each `@Operations.implementation_for(SomeOp)` function takes the op data class and calls `operations.impl.<method>(...)`, where `operations.impl` is the active `DefaultImpl` subclass. This is the bridge between "user wrote `op.add_column(...)`" and "the dialect impl emits SQL."
- **`SchemaObjects` helper**: `operations/schemaobj.py`. Builds throwaway `MetaData`/`Table`/`Column`/`Constraint` instances for ops that need them (e.g. autogenerated `CreateTableOp` from an op definition).
- **Batch operations**: `operations/batch.py`. Implements the copy-and-move strategy for ALTERs on backends with weak DDL.
- **`op` module shim**: `op.py` (and the typed stub `op.pyi`). What user migrations import as `from alembic import op`. Auto-generated proxy to the active `Operations` instance.

## Autogenerate (compare DB state against MetaData, render migrations)

- **Top-level entry**: `autogenerate/api.py`. `produce_migrations(...)`, `compare_metadata(...)`. `AutogenContext` is the per-run state carrier (target metadata, current connection, dialect, options). `RevisionContext` drives revision file production.
- **Comparison pipeline**: `autogenerate/compare/`. Split by concern:
  - `schema.py` — top-level orchestration (`_produce_net_changes`), plugin hook setup.
  - `tables.py` — table add / drop / rename.
  - `constraints.py` — PK / FK / unique / check / index comparison.
  - `types.py` — column type comparison. Calls into `DefaultImpl.compare_type`.
  - `server_defaults.py` — column server-default comparison. Calls into `DefaultImpl.compare_server_default`.
  - `comments.py` — table and column comment comparison.
  - `util.py` — shared helpers.
- **Rendering (op → Python source for migration files)**: `autogenerate/render.py`. `render_op(...)` is the entry; per-op renderers register via `@renderers.dispatch_for(SomeOp)`. Returns the Python source line(s) that will be written into the generated migration script. Important hooks: `render_item` (callable in user env config for custom type rendering), `_repr_type`, `_render_column`.
- **Rewriter**: `autogenerate/rewriter.py`. Lets users programmatically transform the autogen op tree before render.

## Migration runtime (the actual upgrade / downgrade loop)

- **`MigrationContext`**: `runtime/migration.py`. The per-run object that holds the live `Connection`, the active `DefaultImpl`, the `script_directory`, the version table state, and per-step transaction handling. Configured by `EnvironmentContext.configure(...)` in `env.py`. Key methods: `run_migrations`, `_ensure_version_table`, `get_current_heads`, `_catch_revision_errors`.
- **`MigrationStep` / `RevisionStep` / `StampStep`**: `runtime/migration.py`. One step per revision in the up/down plan. `RevisionStep.migration_fn(...)` actually invokes the user's `upgrade()` or `downgrade()`.
- **`EnvironmentContext`**: `runtime/environment.py`. The object exposed inside `env.py` as `context`. Drives `configure(...)`, `begin_transaction(...)`, `run_migrations(...)`. Translates user `env.py` config (URL, target metadata, render_as_batch, transaction_per_migration, etc.) into a `MigrationContext`.
- **`context` shim**: `context.py` (and `context.pyi`). What user `env.py` imports as `from alembic import context`. Proxy to the active `EnvironmentContext`.
- **Plugin discovery**: `runtime/plugins.py`. Setuptools entry points for third-party hooks into autogen comparison.

## Script directory and revision graph

- **`ScriptDirectory`**: `script/base.py`. Owns `versions/`, parses revision files, walks the revision DAG, resolves `head` / `heads` / `base` / branch labels. Methods: `get_revisions`, `iterate_revisions`, `generate_revision`, `_revision_map`.
- **`Revision`**: `script/revision.py`. One node in the graph. Branch labels, dependencies, down_revision, branch_labels, depends_on.
- **Template loading**: `script/base.py` uses Mako templates from `templates/` to render new revision files.

## CLI, config, and entry

- **CLI dispatch**: `__main__.py`, `command.py`. `command.upgrade`, `command.downgrade`, `command.revision`, `command.stamp`, `command.current`, `command.history`, `command.merge`, etc. Each command function is a thin wrapper around `ScriptDirectory` + `MigrationContext`.
- **Config**: `config.py`. Parses `alembic.ini`, holds the `Config` object passed to every command. Important attributes: `config_ini_section`, `get_main_option`, `get_section_option`, `attributes`.
- **Templates** (generated by `alembic init`): `templates/`. `generic/`, `async/`, `multidb/`. The `env.py` template is the entry point most users edit to bind their app's `MetaData` to autogen.

## Testing utilities

- **`testing/`**: in-tree pytest fixtures, `eq_`, `is_`, `assertions`, environment helpers (`MigrationTest`, `TestBase`). Third-party impls can write tests against these.

## Errors and util

- **`util/exc.py`**: `CommandError`, `AutogenerateDiffsDetected`. Most user-facing errors come from `CommandError`.
- **`util/sqla_compat.py`**: SQLAlchemy version compatibility shims. If something works on one SQLAlchemy version but not another, this is the file that explains why.
- **`util/messaging.py`**: stdout / stderr / colored logging — `static_output`, `warn`, `msg`.

## Where ClickHouse integration plugs in
